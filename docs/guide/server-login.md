# 游戏后端登录

游戏后端负责把 KOOK 授权结果转换成游戏自己的可信登录态。SDK 只传递授权码，不接收游戏后端换出的 OAuth token。

## 后端需要完成的步骤

1. 创建不可预测的 `state`，与当前浏览器的登录事务绑定，设置短有效期和一次性消费规则。
2. 收到前端的成功结果后，验证事务仍有效、`state` 匹配、请求来自正确游戏会话。
3. 通过平台约定的 OAuth token 接口交换授权码。应用密钥、access token、refresh token 只在后端保管。
4. 使用平台服务端接口取得可信用户身份。
5. 校验响应属于本游戏应用及当前登录事务，建立游戏账号映射及自己的登录会话。
6. 向浏览器返回游戏需要的展示信息，或通过安全 Cookie 建立会话。不要返回 KOOK OAuth 凭据。

浏览器上送的 `gameCode`、`instanceId`、`roomId` 只能作为提示，不能单独作为用户身份或游戏房间访问权限的凭证。游戏房间的加入资格由游戏后端按自身规则校验。

## 平台接口与配置

在开发者后台配置应用的 `redirect_uri`。**开发者后台目前仍在开发中。** 游戏后端按平台 OAuth 接口要求使用与授权流程一致的 `redirect_uri`；无需通过 `session.get()` 传入该参数。

OAuth 换码地址与应用凭据按平台提供的接入信息配置，应用密钥只保存在游戏后端。公开 scope 为 `get_user_info`（用户信息）和 `mini_game.context`（小游戏上下文）；前者默认申请，后者按需显式追加。`profile.basic` 是兼容别名，SDK 会在发送授权请求前自动映射为 `get_user_info`。

`ready()` 返回的环境信息可用于页面展示与游戏入口处理；用户身份以服务端取得的数据为准，游戏业务权限由游戏后端校验。

## 重试与凭据

授权码是短期、一次性数据。换码结果不明确时由后端按平台协议处理幂等与查询，不要让前端反复提交旧码。需要重新授权时创建新的登录事务。

不要把 code、token、应用密钥写入 URL、埋点或可公开日志。日志记录业务错误码、请求关联标识和阶段即可。前端显示用户信息时使用游戏后端确认的数据。
